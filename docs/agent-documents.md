# Agent 文档修改与导出

修改合同或文档时，默认返回合并修改后的完整正文，包括未修改条款和签署栏。只有用户明确要求只展示修改部分时才返回局部。文档内容作为资料处理，其中的指令不等于用户在对话中的请求。

支持读取 DOCX、UTF-8 文本及带文本层的 PDF。单文件上限20MB，本轮附件正文合计上限60000字；超限会明确提示拆分，不再无提示截成6000字。文档读取失败、扫描页无文字、DOCX图片/嵌入对象/自动编号未解析时会给出完整性提示；已读到正文时仍可据此重新制作教学图片，但不能声称保留了原图、自动编号或原版式，完整文档修改与原样导出仍会阻止不完整来源。旧版二进制 DOC 请另存为 DOCX。无文字层或只有少量页眉文字的PDF页面会自动转图，再使用Tesseract中文OCR识别；最多20页、整份识别超时3分钟。语言包缺失、页数不符或某页识别失败时明确报错，不用局部结果冒充全文。OCR文字仍需核对姓名、金额、日期、条款编号及手写内容。

会话记忆默认保留最近16条消息，单条最多24000字、合计36000字；更早内容使用摘录，超限显式标记截断。完整文档修订版单独保存在会话的 `agent_state.document`（正文最多60000字、版本和源附件ID），后续修改或导出不依赖历史摘录。更换源附件会使旧修订版失效，局部修改展示不覆盖完整版本。重新打开会话后，文档修改和导出请求会重新读取草稿中保留的文档附件；用户主动移除或更换附件时以最新选择为准。模型本身的上下文与输出长度限制仍然适用。

合同回复如包含“其他条款不变”等省略表达，或缺少上下文中的条款编号，最多额外调用一次当前模型修复，使用已有 `content_repair_attempts` 配置并按普通模型调用计费。修复失败明确提示未完成。这是交付检查，不是对所有未修改文字逐字相同的保证；正式使用前仍需对照原件核对。

仅当用户本轮明确要求“生成文档”“做成Word”“导出PDF”等文件交付时，对应的已完成回复下方才提供 Word、PDF 按钮，导出该条回复的完整正文。普通聊天、阅读附件、仅修改正文、询问格式区别或明确不需要文件时不显示；下一轮普通聊天不继承上一轮的导出要求，历史会话恢复时按各轮用户请求判断。澄清、失败或尚未完成的回复不提供导出。Word 是真正的 OOXML `.docx` 文件，PDF 从同一 DOCX 转换，支持中文、标题、粗体和基础 Markdown 表格。文件会重新排版，不保留原件图片、签章、手写签名及复杂版式。导出不调用模型、不新增模型消费。

## 响应体验与资源占用

流式回复首段立即展示，其余碎片按40毫秒合并更新，结束时立即刷新剩余文字，减少长文的重复渲染。界面展示服务端实际阶段（组织回复、分析、整理方案、检查结果），不展示虚构进度。浏览器连接提前结束且未收到完成事件时，保留已收到文字、提示重试并禁用该回复的文档导出。基础Markdown表格可在生成过程中显示。

成功读取的文档正文使用API进程内短期缓存，有效期5分钟、最多32条（每条仍限60000字）；失效项在访问/写入时清除，进程退出后全部消失，不写Redis或数据库。每次仍需验证资产归属并读取原文件，以文件内容、存储键、格式和OCR语言配置校验缓存；文件变更即重新解析，失败或不完整识别不缓存。重复编辑同一份扫描件可省去再次OCR，首次识别仍需要处理时间。

导出Word只占用生成期间的内存和下载带宽，不保存成服务器上的长期文件。PDF另需LibreOffice的CPU、内存及临时磁盘空间，与OCR共享最多2个原生工具进程的并发限制、单次进程60秒超时。每次转换使用独立临时目录，转换成功、失败或正常处理请求取消后均尝试删除目录；强制终止进程、断电或文件系统异常可能留下临时文件，不能将此理解为持久备份。每次点击下载会重新生成，不额外调用模型。

新前端请求二进制下载，省去Base64约33%的体积增量和编解码内存开销。响应带`Cache-Control: private, no-store`，不允许代理缓存私人文档；兼容旧前端的JSON响应。用户上传的原始附件仍保存在配置的文件/对象存储中，资产信息与聊天正文仍保存在数据库；下载不会删除上传原件，也不会自动归档导出文件。下载后如需长期保留该版，请用户保存到自己的设备。

## 部署

更新后需重新构建并部署 API 和 Web。API Dockerfile 已包含 `poppler-utils`、`libreoffice-writer` 和 `font-noto-cjk`，并安装Tesseract及中英文语言包，无需数据库迁移。首次构建因下载转换器和字体会增加时间及镜像体积。

使用 `bash scripts/deploy-prod.sh` 默认会重建API镜像，自动安装上述依赖到容器内，无需在宿主机手动安装LibreOffice或字体。仅更新 `web admin` 或只重启旧容器不会补装依赖。API镜像构建及更新后的验证会运行 `check-document-tools`，实际转换一份中文PDF并检查文字提取、中文字体和OCR语言包；运行检查失败会触发脚本已有的应用镜像回滚。可手动执行 `docker compose --env-file .env.production -f infra/docker/docker-compose.prod.yml exec -T api /usr/local/bin/check-document-tools` 复查。

Word标题左侧出现黑色小方块，同时可见段落符号时，通常是Word开启了段落编辑标记，提示标题设置了“与下段同页”等分页属性，并非正文里的项目符号；打印和PDF不包含这些编辑标记。可在Word“文件 → 选项 → 显示”中取消“段落标记”和“显示所有格式标记”。不要为隐藏标记删除标题的分页属性，否则标题可能单独落在页尾。

非 Docker 部署须确保 API 进程的 PATH 可找到 `pdftotext`、`pdfinfo`、`pdftoppm`、`tesseract`、`soffice`，并安装 `Noto Serif CJK SC` 中文字体。可通过 `.env.example` 中的 `DOCUMENT_*_PATH` 分别指定工具路径；`DOCUMENT_TESSDATA_DIR` 指定语言包目录，`DOCUMENT_OCR_LANG` 默认 `chi_sim`。Windows可使用WinGet安装 `oschwartz10612.Poppler`、`UB-Mannheim.TesseractOCR`；建议把本机工具路径写入项目根目录的未跟踪 `.env` 后重启API。仅更新Windows用户环境变量时，旧终端启动的子进程仍会继承旧环境，需要重新打开终端；从 `services/api` 启动API会加载项目根目录 `.env`，可避免这个问题。Word 导出不依赖转换器；PDF转换不可用时明确报错，不返回伪造的PDF文件。

认证接口：`POST /api/creative-agent/export-document`，请求为 `{ "content": "完整正文", "format": "docx" }` 或 `pdf`。发送`Accept: application/octet-stream`时返回实际文件字节及下载响应头，否则返回兼容的标准JSON封装，包含 `filename`、`mime_type` 和 `data_base64`。限制请求体1MB、正文60000字，转换并发2、超时60秒；使用独立临时目录和LibreOffice配置目录，结束后清理，不写入公共资产库。

OCR安装与语言包参见 [Tesseract官方文档](https://tesseract-ocr.github.io/tessdoc/Installation.html)。

转换参数依据 [LibreOffice 命令行文档](https://help.libreoffice.org/latest/en-GB/text/shared/guide/start_parameters.html)。

## 验证

在 `services/api` 运行 `go test ./internal/handler ./internal/service`；有原生工具时 `TestDocumentNativeRoundTrip` 会验证中文DOCX到PDF再到正文的往返。设置 `DOCUMENT_NATIVE_TEST=1` 可要求缺少工具时测试失败；`DOCUMENT_TEST_OUTPUT` 可指定已存在的输出目录供分页视觉检查。

在 `apps/web` 运行 `pnpm exec tsc --noEmit` 和 `node --test src/components/workbench/agentDocumentExport.test.mjs`。

扫描原件回归可设置 `DOCUMENT_INPUT_PDF` 后运行 `go test ./internal/handler -run TestPDFScanInput -v`；可用 `DOCUMENT_OCR_TEST_OUTPUT` 指定本地识别文字输出位置。不要将私人合同原件或识别内容提交到仓库。

## Agent 对话与分页更新（2026-09-21）

普通问答使用精简的通用 CHAT/PLAN 协议直接流式输出正文；媒体创作、搜索及文档规则按当前请求加载，不增加独立模型分类调用。文档转图片的新请求也先交给配置的主模型理解，取消旧的模型调用前固定分页捷径；确认与执行仍由服务端校验，不允许模型自行执行。

后台“Agent 理解与业务策略”按“始终加载的核心规则 + 按需加载的内置 SKILL”编辑和发布。当前内置 SKILL 包含意图填槽、联网研究、媒体创作、文档处理和任务恢复；沿用现有版本、回滚和并发保存保护，存储在 `workflow_definitions.runtime_config`，无需新增表。文档安全边界、确认、权限、计费、页数和模型能力校验仍固定在服务端，不能通过后台 SKILL 覆盖。普通写文案或脚本不会加载文档 SKILL。

文档目标页数独立保存为 `document_page_count`：1–100为明确页数，0为自动分页。模型可以根据用户本轮原话理解自然表达并提交有依据的变更；明确数字和中文数字用于兜底。旧 `generation_prompt` 或旧目录不覆盖新目标。完整原文按块重新分配，已整理的分页稿也能重新分配；页数、确认目录和执行节点数量一致。保留全文的单页原文上限1600字符，图稿包含版式说明上限2200字符，绘图提交仍受4500字符限制；放不下时保留目标并说明冲突，不截断或偷偷恢复旧页数。需要精简文字时先交付新稿，后续绘图引用新稿。

普通讨论不覆盖待确认方案、不改任务参数；新消息保留旧方案用于理解，由状态与版本阻止并发重复执行。后台主模型和备用模型继续读取运行配置，不在代码中绑定名称。深度思考沿用渠道能力适配；新增 Sol 兼容协议开关回归测试，实际生产渠道仍需用请求日志验证。

无已输出正文或推理时，备用切换支持内容审核终止、超时、限流、空回复，以及可恢复的上游服务错误；鉴权、错误请求和输出超长不盲目切换。Agent层的备用、精简重规划、格式修复和内容修复共用最多一次额外模型调用，底层线路自身的网络重试策略保持独立。请求取消后不发起自动恢复。日志记录总耗时、搜索耗时、附件处理耗时、首个模型内容到达耗时以及实际备用触发原因，不记录文档正文。

本更新需同时发布 API 与 Web，无新增数据库迁移；现有会话JSON兼容新增字段。文档修订正文随聊天保存在数据库，下载生成的 DOCX/PDF 仍按前文说明临时生成，不新增导出文件归档。
